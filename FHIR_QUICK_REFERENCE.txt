AUTHORIZATION CODE FLOW (MOST COMMON - 99% of cases)
================================================================================

USER INITIATES LOGIN:
  Browser → /login

STEP 1: FRONTEND REDIRECTS TO EMR
  Frontend redirects to:
    {authorization_endpoint}?response_type=code&client_id=X&redirect_uri=Y
    &scope=patient/Patient.rs%20offline_access&state=RANDOM
    &code_challenge=PKCE_HASH&code_challenge_method=S256

  Where {authorization_endpoint} comes from:
    GET {fhir_base_url}/.well-known/smart-configuration

STEP 2: USER LOGS IN AT EMR
  User sees EMR's login screen
  EMR validates credentials
  EMR asks user to approve permissions

STEP 3: EMR REDIRECTS BACK TO YOUR APP
  {redirect_uri}?code=AUTH_CODE&state=SAME_STATE

STEP 4: BACKEND EXCHANGES CODE FOR TOKENS (Server-to-server, HTTPS)
  POST {token_endpoint}
  Content-Type: application/x-www-form-urlencoded

  grant_type=authorization_code
  &code=AUTH_CODE
  &client_id=YOUR_CLIENT_ID
  &client_secret=YOUR_CLIENT_SECRET
  &code_verifier=ORIGINAL_PKCE_VERIFIER

  Response:
  {
    "access_token": "eyJ...",          ← Use this for FHIR API calls
    "token_type": "Bearer",
    "expires_in": 3600,                ← Expires in 1 hour
    "refresh_token": "eyJ...",         ← Store encrypted, never expose
    "refresh_token_expires_in": 2592000 ← Expires in 30 days
  }

STEP 5: USE TOKEN TO CALL FHIR API
  GET {fhir_base_url}/Patient/123
  Authorization: Bearer eyJ...

  GET {fhir_base_url}/Condition?subject=Patient/123
  GET {fhir_base_url}/Observation?subject=Patient/123

STEP 6: BEFORE TOKEN EXPIRES, REFRESH
  POST {token_endpoint}
  grant_type=refresh_token
  &refresh_token=STORED_REFRESH_TOKEN
  &client_id=YOUR_CLIENT_ID
  &client_secret=YOUR_CLIENT_SECRET

  Response: New access_token (store new refresh_token too)

================================================================================
BACKEND SERVICES FLOW (For batch/scheduled jobs, NO user login)
================================================================================

PRE-REQUISITE: Register with EMR using JWT authentication
  Send: client_name, token_endpoint_auth_method=private_key_jwt
  Receive: client_id

GENERATE JWT ASSERTION (do this for each token request):
  {
    "iss": "YOUR_CLIENT_ID",
    "sub": "YOUR_CLIENT_ID",
    "aud": "{token_endpoint_url}",
    "exp": now + 5 minutes,
    "jti": "unique-nonce-12345"
  }
  Sign with RS384 using your private key

REQUEST ACCESS TOKEN:
  POST {token_endpoint}

  grant_type=client_credentials
  &client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer
  &client_assertion=SIGNED_JWT
  &scope=system/Patient.rs%20system/Condition.rs

USE TOKEN (very short-lived, 60-300 seconds):
  GET {fhir_base_url}/Patient
  Authorization: Bearer eyJ...

NOTE: Do NOT try to refresh. Generate new JWT & request new token.

================================================================================
CRITICAL: TOKEN STORAGE ARCHITECTURE
================================================================================

FRONTEND:
  - NEVER store tokens in localStorage
  - NEVER store tokens in sessionStorage
  - NEVER log tokens
  - ONLY store in memory (lost on page refresh - acceptable)

BACKEND:
  - Store in DATABASE, encrypted with AES-256-GCM
  - Access token: Can be in memory (short-lived: 1 hour)
  - Refresh token: MUST be in encrypted database
  - Use environment variable for encryption key

DATABASE SCHEMA (minimum):
  oauth_tokens {
    id UUID,
    user_id UUID,
    tenant_id UUID,
    access_token TEXT (AES-256 encrypted),
    refresh_token TEXT (AES-256 encrypted),
    access_token_expires_at TIMESTAMP,
    refresh_token_expires_at TIMESTAMP,
    emr_system VARCHAR (epic/cerner/openemr),
    emr_connection_id UUID,
    scopes TEXT,
    revoked_at TIMESTAMP
  }

ENCRYPTION PATTERN:
  const encrypted = encrypt(token, ENCRYPTION_KEY);  // AES-256-GCM
  const decrypted = decrypt(encrypted, ENCRYPTION_KEY);

TOKEN USAGE:
  1. Check if expired (with 5-min buffer)
  2. If expired, refresh immediately
  3. Use access token in Authorization header
  4. On 401, refresh and retry

MULTI-TENANT ARCHITECTURE (Essential for SaaS)
================================================================================

DATABASE STRUCTURE:

  tenants {
    id UUID PRIMARY KEY,
    name VARCHAR,
    status VARCHAR
  }

  emr_connections {
    id UUID PRIMARY KEY,
    tenant_id UUID (FK → tenants),
    emr_system VARCHAR (epic/cerner/openemr),
    fhir_base_url TEXT,
    oauth_base_url TEXT,
    client_id VARCHAR,
    client_secret TEXT (encrypted),
    status VARCHAR
  }

  oauth_tokens {
    id UUID PRIMARY KEY,
    tenant_id UUID (FK → tenants),
    user_id UUID (FK → users),
    emr_connection_id UUID (FK → emr_connections),
    access_token_encrypted TEXT,
    refresh_token_encrypted TEXT,
    ... (rest of fields)
  }

KEY PRINCIPLE: Every query includes tenant_id
  - SELECT * FROM oauth_tokens WHERE tenant_id = $1 AND user_id = $2
  - Prevents token leakage between customers
  - Audit trail is per-tenant

MULTI-TENANT ISOLATION CHECKLIST:
  ✓ Every token tied to specific tenant_id
  ✓ Middleware enforces user can only access own tenant
  ✓ FHIR API calls go to correct EMR per connection
  ✓ One user can have multiple EMR connections (different hospitals)
  ✓ Audit logging includes tenant_id
  ✓ No shared EMR connections across tenants

SUPPORTED SCOPES (All EMRs support these):
  openid                           (Required for identity)
  offline_access                   (Long-lived refresh token)
  online_access                    (Short-lived session)
  patient/Patient.read             (Read patient demographics)
  patient/Patient.rs               (Read + search)
  patient/Observation.read         (Read labs/vitals)
  patient/Observation.rs           (Read + search)
  patient/Condition.read           (Read diagnoses)
  patient/Condition.rs             (Read + search)
  system/Patient.rs                (Backend: all patients)
  system/Condition.rs              (Backend: all conditions)

FHIR RESOURCES (Standard across all EMRs):
  /Patient/{id}                    Get patient demographics
  /Condition?subject=Patient/{id}  Get conditions (diagnoses)
  /Observation?subject=Patient/{id} Get observations (labs, vitals)
  /Encounter?subject=Patient/{id}  Get encounters (visits)
  /MedicationRequest?subject=...   Get medications
  /AllergyIntolerance?patient=...  Get allergies

OAUTH2 ERRORS (What they mean & how to handle)
================================================================================

400 Invalid Request
  → Missing or invalid parameter
  → Check your request syntax
  → Don't retry

401 Invalid Client
  → Client ID/secret wrong or not registered
  → Check credentials
  → Don't retry

401 Invalid Grant
  → Authorization code expired (usually 10-15 minutes)
  → Code already used
  → New code required, redirect user to login again

401 Unauthorized (on API call)
  → Access token expired
  → Refresh token and retry
  → If refresh fails, user must re-authenticate

403 Forbidden
  → Token doesn't have required scope
  → Refresh and request again
  → If still fails, user must re-authenticate with more scopes

429 Too Many Requests
  → Rate limit exceeded
  → Backoff and retry (exponential: 1s, 2s, 4s, 8s...)
  → Check Retry-After header

500+ Server Error
  → EMR server error (temporary)
  → Retry with exponential backoff
  → Max 3-5 retries

PKCE (PROOF KEY FOR CODE EXCHANGE) - REQUIRED
================================================================================

WHY: Protects against authorization code interception attacks

IMPLEMENTATION:

  1. Generate CODE VERIFIER (43-128 random chars):
     crypto.randomBytes(32).toString('base64url')
     Result: dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk

  2. Create CODE CHALLENGE (SHA256 hash of verifier):
     Base64URL(SHA256(verifier))
     Result: E9Mrozoa2owUednw8ZG4Q1eRvMJ34G5LP7PEcde7Qg8

  3. Send code_challenge in authorization request:
     &code_challenge=E9Mrozoa2owUednw8ZG4Q1eRvMJ34G5LP7PEcde7Qg8
     &code_challenge_method=S256

  4. Send code_verifier in token request:
     &code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk

  EMR verifies: SHA256(code_verifier) == code_challenge
  If match: Authorization code is valid
  If no match: Code rejected

KEY POINTS:
  • ALWAYS use S256 method (never "plain")
  • Code verifier = random, known only to your app
  • Code challenge = hash sent to EMR
  • Even if auth code intercepted, attacker can't use it (no verifier)

ERROR RECOVERY PATTERNS (Code-level)
================================================================================

PATTERN 1: Auto-refresh before expiration (RECOMMENDED)
  if (token.expiresAt - now < 5_MINUTES) {
    token = refreshAccessToken(token);
  }
  return token;

PATTERN 2: Retry on 401
  try {
    return callFHIRAPI(token);
  } catch (error) {
    if (error.status === 401) {
      token = refreshAccessToken(token);
      return callFHIRAPI(token);
    }
    throw error;
  }

PATTERN 3: Exponential backoff on 5xx/429
  for (let attempt = 1; attempt <= 3; attempt++) {
    try {
      return callFHIRAPI(token);
    } catch (error) {
      if (error.status >= 500 || error.status === 429) {
        const delay = Math.pow(2, attempt - 1) * 1000;
        await sleep(delay);
        continue;
      }
      throw error;
    }
  }

PATTERN 4: Comprehensive retry
  ✓ 401 (expired token): Refresh and retry
  ✓ 403 (no scope): Re-authenticate (get more scopes)
  ✓ 404 (not found): Don't retry
  ✓ 429 (rate limit): Backoff and retry
  ✓ 500+ (server error): Backoff and retry
  ✓ Network error: Backoff and retry

COMMON MISTAKES
================================================================================

❌ Storing tokens in localStorage
   Fix: Backend for Frontend pattern

❌ Using "plain" PKCE
   Fix: Always use S256

❌ Not validating state parameter
   Fix: Validate on every callback

❌ Hardcoding EMR URLs
   Fix: Use .well-known/smart-configuration discovery

❌ Only refreshing at login
   Fix: Check and refresh before every API call

❌ Storing unencrypted tokens
   Fix: AES-256-GCM encryption

❌ No audit logging
   Fix: Log all token access and FHIR calls

❌ Sharing tokens across tenants
   Fix: Use (tenant_id, user_id) tuple key

❌ No error recovery
   Fix: Retry with exponential backoff

❌ Ignoring rate limits
   Fix: Implement backoff strategy
